# Broker credential vault and connection lifecycle

## Security boundary

Broker API credentials are secrets, not ordinary connection metadata. The application must never persist plaintext credentials, return them after save, log them, put them in browser storage, or include them in source control.

The API now uses AWS KMS envelope encryption:
- Each connection gets a unique AES-256 data key generated by AWS KMS.
- The credential JSON is encrypted with AES-256-GCM and a fixed application/purpose/version AAD.
- The encrypted data key, nonce, authentication tag and ciphertext are stored together in the existing BrokerConnection.encryptedSecret BYTEA field.
- KMS encryption context binds the encrypted data key to this application's broker-credential purpose.
- Decryption is server-only and is reserved for provider adapter calls.
- The API uses the AWS SDK default credential chain. Production must use a narrowly scoped ECS task role; do not use long-lived IAM user keys.

Required production configuration:
- AWS_REGION=ap-south-1
- BROKER_SECRETS_KMS_KEY_ID=<customer-managed KMS key ARN or ID>
- IAM permissions limited to kms:GenerateDataKey and kms:Decrypt on that exact key, constrained by encryption context where possible.

No AWS resources have been provisioned. No spend has been incurred by this code change. Until the KMS key and IAM role are configured, the credential API returns 503 and stores nothing. Do not use a local plaintext or static AES key fallback.

## Current API behavior

- GET /api/v1/brokers/providers returns sanitized provider auth metadata and the exact fields supported by the credential endpoint.
- POST /api/v1/brokers/connections requires an authenticated user, trusted Origin, rate limit and exact provider-specific credential keys. It encrypts credentials before writing a tenant-owned BrokerConnection record.
- Only DhanHQ access token, Groww access token and Delta Exchange India API key/secret currently accept credentials. All three remain PENDING and are not executable until a provider-specific account identity, permissions and health test is implemented.
- OAuth-based providers (Zerodha, Angel One, Upstox, FYERS, Shoonya, Flattrade, 5paisa, ICICI Breeze, Alice Blue) deliberately reject generic credential submission. Their OAuth state/callback/token-exchange flows must be implemented individually.
- DELETE /api/v1/brokers/connections/:connectionId is tenant-scoped; subscriptions using that destination are paused and detached before deletion.

## Remaining production requirements

1. Configure a customer-managed KMS key and least-privilege ECS task role in Mumbai after explicit infrastructure approval.
2. Add a verified provider identity check and provider health adapter before changing PENDING to CONNECTED.
3. Add secret rotation/re-encryption and KMS key rotation runbooks.
4. Add provider-specific OAuth state records, PKCE/state validation where supported, exact redirect URI allowlists, callback replay protection and token exchange.
5. Add static egress IP verification and provider-side allowlist status before enabling order permissions.
6. Add account ownership confirmation, audit trails, deletion/retention policy and secret access metrics.
7. Complete a threat model, penetration test and security review before real broker credentials are used.
8. Do not enable order placement until capability tests and written broker/legal approvals pass.

A saved credential is not a connected broker, and a connected broker is not a live-trading approval.
